# 航空餐食按需履约

约定航班餐食选择、供应批次、装载和替代权益的处理方式，并把履约链上的关键不变量做成可核对的检查。

## 领域资料

`contracts/` 下的 JSON Schema 约定各类基础资料格式，`fixtures/` 提供不含真实个人信息的虚构示例。代码模块只负责读取和校验这些资料，后续业务服务可以沿用其中的领域标识与版本约定。

当前资料记录了以下业务事实：

- 航司提供弃餐换里程或优惠券
- 特殊旅客仍享有免费特殊餐保障
- 延误场景可向旅客发放机场电子餐券
- 值机截止、配餐装车、登机口变化与起飞之间分阶段冻结履约数据
- 退票、升舱、航班合并、退款、积分与优惠券调整保持守恒
- 同一权益不可重复兑现，离线补录按幂等键去重
- 乘务组仅获取唯一有效装载版本，过敏信息最小可见
- 跨机场补配与供应商替换不得改变有效装载总量

## 契约

| 契约 | 内容 |
| --- | --- |
| `contracts/flight.schema.json` | 航班、航段、当前履约阶段与退改政策参数 |
| `contracts/supplier.schema.json` | 供应商服务机场与餐型能力 |
| `contracts/passenger.schema.json` | 脱敏旅客： opaque 引用、打码姓名、座位、特殊需求与过敏原编码，不含明文身份信息 |
| `contracts/entitlement.schema.json` | 餐食权益：标准餐、特殊保障餐、付费升舱、弃餐换里程/券、延误餐券 |
| `contracts/manifest.schema.json` | 装载版本：餐食行、供应批次（含替换与跨机场补配）、渠道再分配 |
| `contracts/ledger.schema.json` | 守恒账目：积分、支付、退款、优惠券、餐券的借贷记录 |
| `contracts/redemption.schema.json` | 权益兑现记录，含幂等键以支持离线补录去重 |

## 履约链阶段与冻结

阶段顺序：`checkin_closed`（值机截止）→ `catering_loaded`（配餐装车）→ `gate_final`（登机口确认）→ `departed`（起飞）。

- 越过 `catering_loaded` 后，餐食行与供应批次冻结
- 越过 `gate_final` 后，渠道再分配冻结
- 起飞后不得再生成装载新版本
- 每次变更生成新版本：版本号连续递增、声明 `supersedes` 替代关系，且每个航班任意时刻只有一个 `effective` 版本，乘务组只读取该版本

## 不变量检查（`src/`）

- `stages.js`：版本演进不得回退阶段、不得修改已冻结区段
- `manifest.js`：唯一有效版本、替代链完整；装载守恒（供应商替换需双向标记且餐型数量不变，跨机场批次必须对应缺口，有效装载总量等于需求）；乘务组视图与过敏信息最小可见
- `conservation.js`：每份权益的积分/支付/退款/优惠券/餐券账目与政策推导值逐笔对应，不多不少；航班合并时承接权益与原权益在旅客、餐型与价值上守恒
- `redemption.js`：同一权益不得兑现两次，离线补录按幂等键去重，兑现必须对应当前唯一有效装载版本
- `guarantee.js`：儿童、低糖等特殊旅客的基础保障餐不可被弃餐、升级或合并移除

## 本地校验

```sh
npm test
```

测试会确认示例资料符合全部契约、样例场景满足全部不变量，并对各类破坏场景（重复兑现、冻结后修改、账目不守恒、保障缺失、过敏原越界可见等）必须报错。示例中的编号均为虚构值，不包含账号、凭据或真实主体信息。
